# Session 8: It has not learnt

3 October 2026 | Neetesh Jain | 2025MB26095

---

A participant described a requirements tool that only became usable on the sixth or seventh reject. Same prompt. Click reject. Try again. Confidence gone by attempt two. Something usable by attempt six.

I recognised the loop. I have done it with coding assistants for months and called it working with the tool. The faculty's reading was simpler. The system is choosing from a set of alternatives. Each rejection throws one away. It has not learnt. Learnt would mean the weights changed and were saved and reused on the next start. Restart it and the old habit is back.

That distinction belongs in the PRD. Our agent will look as if it improved when a manager rejects a bad action, because the next proposal in the same session may be better. It has not improved. It has only used up some of the bad options in memory. Next Monday it starts again. If we report that as learning, we are lying in the metrics I am supposed to own.

**Prototype answering the wrong question.** The instruction was to pick the smallest, cheapest thing that gives you enough to decide, and to be honest if a non AI solution is better. Our adversarial session already produced that objection: a Flow plus a dashboard might capture most of the value. I had treated that as an examiner risk. This session made it a gate. If the prototype cannot beat that Flow on the one job that matters, ranking attention, we should not fund the next stage.

The other trap named was hidden human labour. Some vendors said it was AI and a person was doing it behind the scenes. For a tiny workflow test that can be honest. As a production design it does not scale, and you still have not learnt how to build the decisioning. Our approval gate is not that trap, because we say the human commits it. The trap for us is the opposite. We might keep the human in so long that we never find out whether the ranking is actually good.

**Earn the right to pass the gate.** Do not let teams advance without demonstrating something, and write the go or no go criteria before the spend, not after. I have lived the other version. ISO audits where you backdate a review because the project is already in stage five and you are still recording stage one. That is theatre. Our roadmap already has evidence gates. What it does not have is a time limit on the decision. Holding a team while you think is also a cost. I will put a decision window on each gate so the process aids progress instead of becoming the delay.

**What I will stop doing.** Treating a better sixth attempt as a better system. It is a narrower remaining set, and it resets.
