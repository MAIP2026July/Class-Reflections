## 1. Class Context

The first class after the midterm focused on building products on AI that keeps changing. It covered when rules beat LLMs, keeping vendors pluggable, hidden AI assumptions, learning before automating, and the gates between prototype, pilot and MVP.

## 2. Key Takeaways

- **Use the right tool for the query:** Deterministic needs such as calculations or lookups belong to rules or APIs, while retrieval suits semantic search. One large vector store is not a universal answer.
- **Keep vendors pluggable:** Model and provider behaviour can change, so the architecture should allow switching without rewriting the product.
- **Watch for silent assumptions:** The professor's three banks example showed how AI tools can turn a test value into a permanent rule.
- **Learn before we automate:** Route low-confidence cases to humans, keep manual fallbacks and avoid premature automation.
- **Be honest about manual steps:** Partial automation is fine if the core value is strong and the manual parts are stated openly.
- **Prototype, pilot and MVP differ:** Prototypes are for demos, pilots test value with real customers, and an MVP must deliver core value even without every integration.
- **Single-threaded ownership and gates:** Teams should earn the right to move to the next stage, and governance should stay minimal and right-sized.

## 3. My Reflection as a Product Manager

- **Provider instability is now a product risk.** I used to see model changes as an engineering matter. The class made me see that a silent change in a vendor model can change customer outcomes without any release from our side, so monitoring belongs in the product plan.
- **The three banks example felt very familiar.** Requirements and test data can quietly become permanent constraints. Reviewing AI-generated work for hidden assumptions is part of the PM's quality responsibility.
- **Honesty about manual work builds trust.** In implementation-heavy products, admitting which steps are still manual is better than overstating automation and losing credibility later.
- **Gates protect teams as well as investment.** Clear success criteria before a pilot prevent endless additions that drain the team.
- **Where I differ:** Minimal governance is right, but in healthcare some gates are non-negotiable. I would keep governance light in process but firm on patient safety and data privacy checks.

## 4. What I Will Carry Forward

- Route deterministic logic to rules and keep AI for judgement tasks.
- Design for model and vendor change from day one.
- Review AI-generated outputs for hidden assumptions.
- Define pilot success criteria and gates before starting.
- State clearly what is still manual in any release.

## 5. Closing Reflection

This class changed how I see AI stability. My key takeaway is that durable AI products depend on pluggable design, honest staging and gates that teams must earn, rather than on any single model being reliable.
