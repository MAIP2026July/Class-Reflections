# Session 6 Reflection - Re-imagining the Workflow, Writing Requirements in the Stakeholder's Language, and Data Risks

## What was familiar under different names

The distinction made in class between requirements and specification is the URS/FS split I work with every day. As mentioned in class, a requirements document should be written in the stakeholder's language ("I as a ride-giver want..."), whereas statements like "the system should handle 10,000 users" belong in a separate product specification. In validation, the User Requirements Specification describes what the business needs, and the Functional Specification describes how the system will do it. Same logic, different names.

The instruction given in class on templates was also familiar: never delete a section, mark it "not applicable" and say why. That is standard validation practice. An N/A without a justification is an audit finding.

## Looking at my current work through this lens

"Stated needs are not always real needs" applies to most report requests I receive. People ask for "a report," but often the real need is an answer to one question an inspector or a QPPV will ask. The crying-child example discussed in class captures this perfectly - the request is the signal, not the requirement. When I build exactly what was asked, I sometimes deliver a beautiful report that answers the wrong question.

Example from my work: A stakeholder once submitted an urgent request for an automated script to export and aggregate every literature search query log into a weekly Excel dashboard. The stated need was a "real-time audit dashboard," but after probing further, the underlying requirement was simply proving to an upcoming regulatory inspector that weekly literature searches were executed on time without missing scheduled runs. Building the massive dashboard would have been a waste; a simple exception-notification alert for missed runs fulfilled the true requirement.

It was also emphasized in class that a wrongly framed problem means the AI "optimises the wrong thing beautifully." If I frame literature screening as "screen faster," the tool will optimise throughput and may miss cases. The real objective is no missed reportable cases within the reporting timeline. Speed is only a constraint.

## What was genuinely new to me

The sentiment quintuple: object, feature, sentiment, opinion holder, time. It maps almost exactly onto the minimum criteria for a valid case. The object is the suspect product, the feature is the adverse event, the opinion holder is the reporter, and time is onset or awareness date. I had never seen opinion mining described in a structure so close to case intake.

The example of the hidden signal presented in class was also new to me. The review mentioned "my mother was mad I didn't tell her," something you would never extract as a feature. In consumer messages for cosmetics and OTC products, a casual line like "my daughter used it too" is a hidden signal of paediatric exposure, a special situation. A tool that extracts only product and complaint would miss it. This is exactly where human-like reading still matters.

## Applying it to something I am planning

For our group project, I want to rewrite our requirements in the "I as a..." form shared in class. For example: "I as a patient on two diabetes medicines want to know if a new prescription interacts with them." Or: "I as a treating clinician want a one-page summary of the patient's reported symptoms before consultation." Any system-level numbers move to the specification section.

For the literature tool, I can now state the ML target in one sentence: for each article and each product, classify it as a valid case, safety-relevant but not a case, or irrelevant. That is a classification problem, not "find relevant articles."

The data risks list from class also applies. A stale product list, testing only on clean English-language abstracts, and a validation set biased toward easy articles would all make the tool look better than it is.

## Where I think it does not fully apply

The black-box exercise from class keeps inputs and outputs fixed and re-imagines what happens inside. In PV the outputs are fixed by regulation: case format, timelines and periodic report structure. So re-imagination can only happen inside the box, never at the output.

The class discussion on consent also works differently for us. Safety data is processed because of a legal obligation, not consent, and the right to erasure gives way to regulatory retention. Purpose limitation still applies, though. Safety data collected for PV cannot be quietly reused for other purposes.

The point made in class that measuring changes behaviour applies here too. If I start tracking minutes per article for reviewers, some will rush to look efficient. I need to measure time and quality together, or not measure time at all.

## What I will do differently

I will rewrite our project's requirements in stakeholder language, with named roles and no unqualified "user." For the literature tool, I will write down the ML target and the business objective as two separate statements before discussing any model.
