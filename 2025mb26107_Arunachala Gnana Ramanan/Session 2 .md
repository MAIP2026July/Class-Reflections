Topic: Product lifecycle (discover → define → strategize → plan → build → launch → grow → retire/renew); PM frameworks; AI-native vs AI-enabled products


This was the session where the framework firehose started — JTBD, double diamond, opportunity solution trees, lean canvas, RICE, Kano, MoSCoW, QFD, Porter's Five Forces, RASCI — and I'll admit my first instinct was mild panic about needing to "know" all of them. What settled that was his repeated point that frameworks are decision aids, not the decision itself, and that picking one small set that fits your context beats trying to run every framework on every problem. That's actually close to how I already operate at work when I'm evaluating vendor proposals, so it was reassuring to have language for something I was doing instinctually.
The idea that landed hardest was the traceability matrix — not as paperwork, but as the mechanism that stops a decision from quietly dying between the meeting where it was made and the release where it should have shown up. I've lived that failure mode: a scope call made in a steering committee that never actually made it into the sprint backlog. I want to try building a lightweight version of this for my own team, even outside this course.
The distinction between AI-enabled products (bolting AI onto something that already exists) and AI-native products (where the product wouldn't have been viable at all without AI) is one I need to hold onto for our own project topic selection — it's an easy line to blur when everyone's under pressure to "use AI" somewhere in the pitch.
