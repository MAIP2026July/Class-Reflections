#Class Reflection — 29 August 2026

The point I took from this class was that believing something has value is not enough; as a product manager I should be able to show evidence of the value.

I find this relevant to software-service activities. Sometimes we add a capability because a customer requested it or because technically it looks useful. After delivery, we may say the feature is successful because it works. But working technically and creating customer value are not necessarily the same thing.

For example, if we create a tool that simplifies BSP build or flashing, technical completion is only one measure. The real value may be reduction in setup time, fewer flashing errors, less dependency on experienced engineers, faster customer onboarding or reduced support effort. These can be measured.

This class also made me rethink opportunity identification. Instead of looking at AI features first, I should look at the existing workflow: where is there repeated manual work, decision stress, high friction, large amounts of data or a trust problem? AI may be useful there, but only after proving that it improves the outcome.

The change I want to make in my work is small but practical. Whenever I propose a new software-service feature, I want to write at least one expected value metric before development starts. After release, I should come back and check whether that expected value really happened.
