# Class Reflection — 21 November 2026

One discussion from this class was very close to my regular work. During the presentation on an AI-assisted ASPICE compliance checker, the professor pointed out that simply identifying a problem is no longer enough. A customer will also expect help to correct the problem, or better still, prevent it from happening. I felt this was a useful way to look at the real value of automation.

In my embedded software team, we spend time on build issues, testing, release documentation and customer-reported problems. Finding a defect is important, but if the same type of defect keeps appearing in different releases, we have not really improved the process. For example, instead of discovering a missing configuration or release document during final validation, a tool could flag it much earlier. This made me think about how we can improve our CI/CD checks and BSP release workflow. I would rather prevent a repeated issue than keep preparing a report about it.

The professor also spoke about **build versus buy**. I had mainly thought of competitors as other companies selling a similar product. In this class, I understood that a customer may build the solution internally, use an existing cloud service, or even continue with a manual process. So, if we propose a new software tool, we should explain why it is worth adopting rather than assuming that using AI makes it valuable. The customer's savings and the product provider's profitability are also two different calculations.

Another point I noted was the trade-off between **cost, response time and accuracy**. The discussion about an AI system answering school enquiries showed why estimating only the price of an LLM request is not sufficient. Retrieval, repeated requests, infrastructure, human review and ongoing support can all affect the actual cost. I also found the questions about software licensing important. A prototype may work technically, but that does not automatically mean it can be offered commercially at the price we planned.

Finally, the professor asked whether a product requirement document is clear enough for someone else to build the solution without constant explanations. That is a practical test of our requirements. My takeaway is to define the problem, expected result, boundaries and acceptance criteria clearly before adding more features. **For me, a successful product is not just one that works in a demo; it should solve a repeated problem, be affordable to operate and give a benefit that customers can actually measure.**
